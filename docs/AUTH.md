# Authentication, profiles and D1

## How it fits together

- **Better Auth 1.7.x** runs inside the Worker (`apps/worker/src/auth.ts`). The D1 binding is passed straight to
  `database` — Better Auth's own D1 support (it detects the binding and uses its D1 dialect). Options live in
  `src/auth-options.ts` and are shared with the schema generator.
- Sign-in methods: **Google OAuth**, **email magic link** (10-minute, single-use) and **guest** (one click, no email). The same verified email is one
  account whichever way you sign in (`accountLinking`, Google trusted).
- Better Auth owns `user`, `session`, `account`, `verification` (migration `0001`, generated by `npx auth generate`,
  the CLI that matches the library version; `npm run auth:schema:check -w apps/worker` fails if it ever drifts).
  Nothing parallel exists; our tables reference `user.id`.
- **Cookie:** `uno.session_token` — `HttpOnly; SameSite=Lax; Path=/`, plus `Secure` and the browser-enforced `__Secure-`
  prefix on https. 30-day lifetime, refreshed daily. The frontend never reads it: it learns who you are from `GET /api/me`.
- **Middleware** (`src/api.ts`): for every `/api/*` request the Worker drops any client `x-user-id`, resolves the session
  from the cookie, injects the user id, and answers 401 on protected routes. State-changing routes also refuse a
  cross-site `Origin`.

## Guest accounts

"Continue as guest" calls Better Auth's anonymous sign-in: it creates a real user flagged `isAnonymous` (placeholder email
`…@guest.uno.invalid`, name `Guest NNNN`) and a normal session cookie, so profiles, preferences, stats and match history all
work exactly as for signed-in players. `/api/me` reports `user.isGuest`; the dashboard shows a banner and the sign-in page
stays reachable so a guest can upgrade.

When a guest later signs in (Google or magic link) Better Auth creates/finds the real account, runs our `mergeGuestInto`
hook, then deletes the guest: match history is re-pointed at the real account, and games/wins/losses are added to its stats
(rating and current streak stay with the real account). The guest's old session stops working.

Not done yet for guests: **limits** (e.g. no ranked games, friends or reports for guests), **clean-up** of abandoned
guest users (a scheduled job to delete guests idle for N days), and **rate limiting** of guest creation (see below).
Guest sign-in needs migration `0004_better_auth_anonymous.sql`; `npm run auth:schema:check -w apps/worker` verifies the auth
tables still match what Better Auth expects.

## Routes

| Method | Path | Notes |
|---|---|---|
| GET | `/api/me` | profile + stats; creates the profile on first call; 401 signed out |
| PATCH | `/api/me/profile` | `displayName` (3–20, letters/digits/spaces, unique ignoring case → 409) and `avatarSeed`. Any other field (wins, elo, …) → 400 |
| PATCH | `/api/me/preferences` | partial update of the preference keys; unknown key or bad value → 400 |
| GET | `/api/me/matches?limit=20` | newest first, 1–100 |
| `*` | `/api/auth/*` | Better Auth (sign-in, callback, sign-out, magic-link verify) |
| GET | `/api/test/magic-link?email=` | e2e only: 404 unless `E2E_SECRET` is set on a non-production deployment |

Errors are `{ "error": { "code", "message" } }`.

## Tables (migrations 0002, 0003)

`user_profiles`, `matches`, `match_players`, `player_stats`, `friendships`, `reports` as specified (timestamps are epoch ms;
display names are unique `COLLATE NOCASE`; deleting an account cascades to its profile and stats but keeps match history
with `user_id` set NULL). `e2e_outbox` holds magic links for automated tests only and is empty in normal use.

## One-time setup for staging (needs your accounts)

1. **Domain.** `staging.uno.example.com` is still the placeholder from Phase 0. Register the real staging domain on
   Cloudflare and replace `uno.example.com` in `apps/worker/wrangler.jsonc`, the workflow, `e2e/` docs and these docs.
2. **D1.** `npx wrangler d1 create uno-staging`; put the printed id in `env.staging.d1_databases[0].database_id`.
3. **Google OAuth client** (Google Cloud Console → APIs & Services → Credentials → OAuth client ID, type *Web application*):
   - Authorised redirect URI: `https://staging.uno.example.com/api/auth/callback/google` (your real domain)
   - Add `https://uno.example.com/api/auth/callback/google` for production, and `http://localhost:8787/api/auth/callback/google` for local dev.
   - OAuth consent screen: External, add yourself as a test user while in Testing.
4. **Secrets** (staging): from `apps/worker`:
   ```
   npx wrangler secret put BETTER_AUTH_SECRET --env staging     # 32+ random chars: openssl rand -base64 48
   npx wrangler secret put GOOGLE_CLIENT_ID --env staging
   npx wrangler secret put GOOGLE_CLIENT_SECRET --env staging
   npx wrangler secret put RESEND_API_KEY --env staging
   npx wrangler secret put MAIL_FROM --env staging              # e.g. UNO <login@your-domain>
   npx wrangler secret put E2E_SECRET --env staging             # staging only, for the Playwright test
   npx wrangler secret put E2E_EMAIL_DOMAIN --env staging       # e.g. e2e.your-domain
   ```
5. **Email.** Magic links are sent through **Resend** (`src/mail.ts`) — an assumption; swap the one `fetch` in that file for
   another provider if you prefer. Verify your sending domain in Resend first. Without these secrets sign-in by email fails
   loudly (500) on staging/production; local dev prints the link to the console instead.
6. **Migrate and deploy:** `npm run db:migrate:staging -w apps/worker` then `npm run deploy:staging` (CI does both).
7. **GitHub:** repository secret `E2E_SECRET` (same value), repository variable `E2E_EMAIL_DOMAIN`.

## Local development

`cp apps/worker/.dev.vars.example apps/worker/.dev.vars`, fill it in, `npm run build`, `npm run db:migrate:local -w apps/worker`,
`npm run dev:worker`, open http://localhost:8787. Without email credentials, magic links print in the Worker's console.

## Not done in this phase

- **Rate limiting** of sign-in attempts. Better Auth's built-in limiter keeps counts in memory, which does not work across
  Worker isolates; it needs a shared store (D1 table or KV) — tracked under roadmap item 43.
- **Account deletion UI, friends and reports** have tables but no routes yet.
